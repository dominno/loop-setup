# Research brief: how people build agentic "code factories" and plan/track tasks (web, 2026-11-06)

External content: claims attributed to web pages (many written by vendors or by other outside publishers), not verified facts.

## Patterns found
1. Anthropic, "Effective harnesses for long-running agents": an INITIALIZER agent expands the prompt into a JSON feature list (200+ items; fields category, description, ordered `steps`, `passes` boolean, all start failing). Each CODING session takes ONE highest-priority unfinished feature, must verify end-to-end as a user (browser automation) before flipping `passes`; may only change `passes` ("unacceptable to remove or edit tests"). Progress file (claude-progress.txt) + git commits; each session starts by reading progress + git log and running a smoke test. JSON chosen because models overwrite Markdown more readily. Failure modes: one-shotting, premature "done", undocumented progress.
2. Beads (Steve Yegge, `bd`): git-backed issue graph for agents. Dependency types blocks / related / parent-child (+ duplicates, supersedes); `bd ready` = no open blockers; closing a blocker releases dependents; `bd update --claim` atomically sets assignee + in_progress; hierarchical ids epic.task.subtask (bd-a3f8.1.1); hash ids avoid merge collisions; old closed issues are compacted ("memory decay"). Reported to have inspired Claude Code Tasks (blockedBy/blocks, shared task list across sessions via an env var).
3. Spec-driven development — GitHub Spec Kit (constitution → specify → clarify → plan → tasks → implement; tasks.md = ordered, dependency-based list grouped by user story, with file paths and [P] parallel markers) and Kiro (requirements.md in EARS → design.md → tasks.md checklist, ≤2 levels, each task tagged `_Requirements: 1.1_` for traceability; live status in the IDE).
4. Taskmaster AI: parse PRD → tasks with dependencies; `analyze-complexity` scores each task 1–10 and recommends a subtask count; `expand` splits high-complexity tasks; `next` picks the next ready task.
5. BMAD method: PRD/architecture "sharded" into small docs; Scrum-Master agent drafts one story at a time with full context; status Draft → Approved (human) → In progress → Review → Done; newer versions keep a sprint-status.yaml (backlog → ready-for-dev → …).
6. GSD (get-shit-done): discuss → plan → execute → verify per phase; fresh sub-agent per atomic task to avoid context rot; persistent state files; plans checked before execution.
7. Plan-driven task decomposition pattern (se-ml agentic patterns): every atomic task = objective, explicit dependencies, scope (files/interfaces), context needed, verification command. Split any task large enough for the agent to "improvise hidden substeps"; track files touched as a size signal; measure split rate and plan drift; anti-patterns: one big task, implicit deps, unreviewed plan, no verification points.
8. ADaPT (Prasad et al., NAACL 2024): decompose AS NEEDED — try to execute; on executor failure, a planner recursively splits only that sub-task (+28% ALFWorld, +27% WebShop, +33% TextCraft vs plan-and-execute). Cost: more LLM calls.
9. METR time horizon: agents succeed 50% on tasks of length H but 80% only on ~H/4 — reliability falls fast with task length → size tasks well below the agent's horizon for unattended work.
10. Factory.ai / MindStudio / Augment: "software factory" = planning decomposes intent into executable steps; humans own intent, review, policy; fully autonomous "dark factories" reported to fail on maintainability.

## How loop-setup plans and tracks today (repo facts)
- `.claude/memory/loop-plan.md`: one flat markdown table of nodes LP-NNN (description, after, status, record, missing, origin, notes); statuses ready/blocked/in-progress/deferred/done/escalated/dropped; ready = all `after` done; `done` needs a loop:<id> accept/qualify record + CLEAR; cascade rules for dropped/escalated deps; defer counts toward a 4-attempt escalation; stale in-progress recovery.
- `scripts/trace/plan.mjs` (pnpm trace plan-ready / plan-lint / plan-items) parses the table, checks DAG + records, builds loop-iteration items (maxItems 5).
- Nodes are created only by the loop's re-plan step from confirmed critic findings (or a human); no hierarchy (no epic/parent), no size/complexity field, no acceptance criteria or verification command per node, no file-scope field, no priority field (table order = priority), no claim/owner for parallel sessions.
- Stories (docs/stories/US-*.md) have their own status ladder (Not started → … → Done) checked by story-lint; story ↔ plan-node link is not modeled.
- The improvement work in this session was planned OUTSIDE loop-plan.md: a Lead-written spec (scratchpad impl-spec.md, "## STEP n" sections with CHANGES/TESTS/VERIFICATION/LEAD AMENDMENTS) driven by an ad-hoc implement workflow (impl → separate verifier → ≤2 fix rounds → commit), with follow-ups added as new steps (11b, 14b, 18a–18g) — i.e. as-needed decomposition done by hand, never recorded in the plan DAG.
