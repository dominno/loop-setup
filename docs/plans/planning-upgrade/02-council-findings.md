## Lens: decomposition
### Atomic-node contract: add `scope` and `check` columns to the plan table, and lint them before a node can be ready
- Verdict: **revise** · priority high · effort M
- Problem: A plan node holds only a one-line `description`. Nothing records which files it touches or which command proves it works. Dispatch still needs both. loop.md step 10 refuses to dispatch two nodes 'expected to touch the same file (the file of their origin finding's file:line)' and skips a node 'whose expected files have uncommitted changes', so the Lead has to work the files out again from the origin record every iteration. The verification command first comes up after the patch is applied ('If no relevant automated check exists, do not CLEAR: HOLD and escalate'). By then the worktree, the implementer and the verifier have already run on a node that could never become `done`. The verifier judges 'in-scope' against a scope that was never written down.
- Evidence: scripts/trace/plan.mjs:16 (PLAN_COLUMNS = id, description, after, status, record, missing, origin, notes: no scope or check); scripts/trace/plan.mjs:93-94 (header must match exactly, so the schema is closed); .claude/memory/loop-plan.md:20 (`description`: 'One line — the bounded unit of work'); .claude/loop.md:131-138 ('expected to touch the same file (the file of their origin finding's file:line)'; 'a node whose expected files have uncommitted changes'); .claude/loop.md step 10 applied branch ('If no relevant automated check exists, do not CLEAR: HOLD and escalate'); .claude/workflows/loop-iteration.js:185 (verifier judges 'correct, in-scope, safe fix for the item' with no stated scope); .claude/workflows/loop-iteration.js:310 (implementer told 'run typecheck, lint and unit tests', with no node-specific check)
- Critic proposal: 1. Add two columns to PLAN_COLUMNS and the loop-plan.md Node schema. `scope` holds the repo-relative files or globs the node may touch, taken from the origin finding's file:line at creation. `check` holds the smallest command that proves the node, for example `pnpm vitest run src/x.test.ts` or a named Playwright spec. 2. Add a plan-lint rule `[contract]`: a `ready` or `blocked` node with an empty `scope` or `check` is an error under `--pre-dispatch`, so a node with no automated check is escalated at re-plan time, not after a worktree run. 3. Make step 10's same-file exclusion and its `git status --porcelain -- <files>` skip read `scope`, not the origin record. 4. Teach the loop-iteration.js denylist gate to also flag a diff whose paths fall outside the node's declared `scope`, as failedGate `scope:<path>` mapped to `revise` (not escalate, see the ADaPT proposal). 5. The plan-items item shape is fixed by the bench ('the bench measured this shape', plan.mjs:322-323). So either re-run /bench-checkers with the extended item `{id, description, scope, check, ...}` before the change lands, or first fold scope and check into `description` as a fixed suffix the bench fixtures already tolerate. Update plan.test.mjs and contracts.test.mjs in step.
- **Skeptic repair (binding, replaces the proposal):** Add `scope` and `check` columns. Make an empty `check` on a ready node an error under --pre-dispatch, and an empty `scope` a warning. Have step 10's same-file exclusion and the git status skip read `scope`. Keep scope and check Lead-side only for now: plan-items still emits {id, description, priorRecordId?, missing?}, so the bench stays valid, and the Lead runs `check` post-apply as the 'smallest relevant check'. Do not add a hard scope gate to loop-iteration.js. Instead, record the diff paths that fall outside `scope` in the run-log entry as a drift signal. Revisit a verifier-visible scope only together with a /bench-checkers re-run. Update plan.test.mjs and contracts.test.mjs in the same commit.
- Skeptic reason: The gap is real. PLAN_COLUMNS (plan.mjs:16) has no scope or check, and the header is matched exactly (plan.mjs:93-94). loop.md step 10 (lines 131-138) makes the Lead work out the expected files again from the origin finding's file:line every iteration. The 'no relevant automated check → HOLD and escalate' rule (loop.md, applied branch) only fires after the implementer and verifier have already run. Migration is cheap: the live table in loop-plan.md is empty, so only test fixtures change. Two parts of the proposal are wrong, though. (a) Step 4 maps an out-of-scope diff to `revise`. The proposal's 'not escalate' only holds if the separate ADaPT proposal lands, so this part depends on another change it does not state. Also, scope comes from a critic's file:line, so it is a guess. Legitimate fixes routinely touch a sibling test file, and a hard deterministic scope gate would produce false escalations. (b) Changing the plan-items item shape invalidates the measured bench: trace-bench.js passes `{id, description}` verbatim to the verifier, and plan.mjs:322-323 says the bench measured that shape. - Research basis: Plan-driven task decomposition pattern: every atomic task has an objective, dependencies, a scope (files/interfaces) and a verification command. Spec Kit tasks.md lists file paths per task. Anthropic long-running-harness feature list gives ordered `steps` per feature. · Risk: The plan header is matched exactly, so every existing plan and test fixture needs a migration in the same commit. A Lead could fill `check` with a trivially passing command, so plan-lint checks the field is present, not that it is meaningful.

### Size signal and split-before-ready rule (complexity score with a hard ceiling for unattended levels)
- Verdict: **revise** · priority high · effort M
- Problem: Nothing measures or caps how big a node is. L2 is limited to 'small, in-scope, low-risk fixes' and the implementer is told 'SMALLEST safe fix', but neither is quantified. A node created from one confirmed critic finding can still cover a multi-file rework, and it is dispatched at the same priority and budget as a one-line fix. At L3 nothing keeps unattended nodes well below the agent's reliable task length.
- Evidence: .claude/loop.md:10-11 (L2: 'small, in-scope, low-risk fixes', unquantified); .claude/workflows/loop-iteration.js:310 ('Implement the SMALLEST safe fix', no bound); .claude/memory/loop-plan.md:14-26 (Node schema: no size or complexity field); scripts/trace/plan.mjs:138-142 (readyIds: readiness depends only on status and after, never on size); .claude/workflows/loop-iteration.js:51-62 (the only quantity limit is maxItems=5 nodes per call, not per-node size)
- Critic proposal: 1. Add a `size` column taking S, M or L, set at node creation from objective signals the Lead records in `notes`: number of files in `scope`, number of acceptance bullets or distinct behaviours, and whether a new test file is needed. Suggested rubric: S = 1 file and 1 behaviour; M = at most 3 files or 2 behaviours; L = anything larger. 2. Split rule in loop-plan.md and loop.md step 9: an L node is never `ready`. Re-plan must split it into S/M children (see the hierarchy proposal) or escalate it as 'architecturally significant', which is already an escalation trigger. 3. Add a plan-lint rule `[oversize]`: error when a `ready` node has size L, or when its `scope` lists more than 3 paths and its size is not L (size understated). 4. Trust-level ceiling in loop-checklist.md: L3 dispatches S only; L2 dispatches S and M. 5. After apply, compare the diff's file count with `scope` and record any overrun in the run-log, so split rate and plan drift can be measured over time.
- **Skeptic repair (binding, replaces the proposal):** Add no `size` column. Derive size from the `scope` column (proposal 1). plan-lint `[oversize]` fails --pre-dispatch when a ready node's scope lists more than N paths, with N = 3. Re-plan must then split the node (proposal 3, revised) or escalate it as architecturally significant. Add the trust-level ceiling to loop-checklist.md: L3 dispatches only nodes with 1 scope path, or lower N at L3. Keep step 5: log the diff file count against scope in the run-log, so split rate and drift are measurable. Land this only after proposal 1.
- Skeptic reason: The gap is real. L2's 'small' (loop.md:10-11) and the implementer's 'SMALLEST safe fix' (loop-iteration.js:310) are unquantified. readyIds (plan.mjs:138-142) ignores size, and maxItems caps only the number of nodes. However, a Lead-declared S/M/L `size` column is self-graded by the same Lead that plans the node, so plan-lint can only check it against the file count anyway. The rubric's other inputs (behaviour count, whether a new test is needed) cannot be checked. A separate column adds schema churn on a denylisted gate for a signal the scope column already carries. The METR H/4 figure is an attributed external claim, not verified here. 'L is never ready' plus the `[oversize]` understatement check comes down to one rule: a path-count ceiling on ready nodes.
- Research basis: Taskmaster `analyze-complexity` (1-10 score plus recommended subtask count) and `expand`; METR time-horizon finding that success falls from 50% at H to 80% only near H/4, hence a size ceiling for unattended work; plan-driven pattern rule 'split any task large enough to improvise hidden substeps', with files touched as the size signal. · Risk: The rubric is a heuristic, and a file count misjudges, for example, a one-file but subtle state-machine change. Keep `size` as a Lead-declared field that lint only bounds from below by file count, never infers. The rule could over-split trivial multi-file renames; the escalate path remains for those.

### ADaPT-style as-needed re-decomposition: a failed node is split, not just retried 4 times then escalated
- Verdict: **revise** · priority high · effort L
- Problem: When a node fails, the loop has two moves: retry the same node unchanged, or escalate it. A post-apply check failure writes a `revise` and 'leave[s] the node `ready`', so the same one-line description is re-dispatched. A verifier `revise` or `reject` sets the node `escalated`. A fourth defer escalates. None of these lets the loop break a too-large or under-specified node into smaller ones, although `revise` already carries a bounded `repair` that often names exactly the missing sub-step. The brief records that this session's own work needed hand-made follow-up steps (11b, 14b, 18a-18g) outside the DAG, which shows the need for as-needed decomposition.
- Evidence: .claude/loop.md step 10 applied branch ('If the check fails, revert the patch, write a revise record ... leave the node ready with that record and the attempt counted'); .claude/loop.md step 10 rejected branch ('rejected (reject/revise/denylist): HOLD, set the node escalated'); .claude/memory/loop-plan.md:42-45 (escalated covers 'a reject/revise verdict'); scripts/trace/plan.mjs:29 (MAX_DEFERS = 3) and :304-307 ([attempts] escalates on the fourth); scripts/trace/plan.mjs:18 (STATUSES has no split or superseded-by-children state)
- Critic proposal: 1. Add a node status `split`, excluded from ready (add it to NOT_READY; it is neither LIVE nor STRANDING). 2. In re-plan step 9, a node whose latest own `loop:<id>` record is a `revise` with a non-empty `repair`, or whose post-apply check failed, or that is on its second attempt, may be split instead of retried. Create 2-4 child nodes, each with a `parent` of the failed id and its own scope and check, and set the parent to `split` with `record` = that revise record, HOLDed `--ref <parent>`. A `reject`, a denylist hit or a human-decision defer still escalates. Splitting never bypasses those. 3. Readiness through a split parent: a dependent of a `split` node is ready only when every child of that node is `done`. In readyIds and planViolations, treat 'P done' as 'P done, or P split and all its children done', transitively. 4. Bounds in plan-lint: children share the parent's attempt budget (`[attempts]` sums the defers and revises on `loop:<parent>` and on all its descendants' claims), and split depth is at most 2 (`[split-depth]`), so the loop cannot split forever to dodge escalation. 5. `[split-record]`: a split node must cite its own revise or defer record with a HOLD, like the existing deferred and escalated checks.
- **Skeptic repair (binding, replaces the proposal):** Add no new status and leave readyIds unchanged. In re-plan step 9, allow a split only for (i) a node's own `loop:<id>` revise with a non-empty repair, or (ii) a post-apply check failure, and only at L2 at first. To split: `drop` the parent with a note 'split into LP-a, LP-b', HOLD its revise record `--ref` the parent, and create 2-4 children with origin `split from <parent> rec:<revise id>`, each with its own scope and check. Re-point the parent's dependents' `after:` to all the children. Never split a reject, a denylist hit or a human-decision defer. Add these plan-lint rules: `[split-origin]` (the cited record is the parent's own revise and the parent is dropped); `[split-depth]` (at most 2, following origin chains); and an attempts count that includes revises as well as defers, summed over the split lineage.
- Skeptic reason: The gap is real. A verifier revise escalates the node (loop.md rejected branch; loop-plan.md:42-45). A post-apply check failure leaves the node ready with the same description. No path turns a bounded `repair` into smaller nodes. The proposed mechanism is more than this needs, and it is risky. A new `split` status plus transitive readiness ('P done or P split and all children done') changes readyIds and planViolations, which are the most safety-critical denylisted gate. The repo already expresses the same thing with existing primitives: re-plan may `drop` a node and 're-point its after: to a live node' (loop-plan.md, Cascading drop), so dependents can be re-pointed to all the children. No readiness change is needed. Separately, the attempt budget is undercounted today. `[attempts]` counts only defer records (plan.mjs:235-236, 304-307), not the revises a post-apply failure writes, so 'children share the parent's attempt budget' cannot be built on the existing counter as is. The '11b, 14b, 18a-18g' evidence is the brief's account of this session's hand-driven spec work, not loop behaviour.
- Research basis: ADaPT (Prasad et al., NAACL 2024): execute first, and on executor failure recursively decompose only the failing sub-task (reported +27-33% over plan-and-execute). Kiro's limit of 2 levels for the depth bound. · Risk: This adds a new state to the most safety-critical gate (plan.mjs is denylisted, so a human must land it), and the readiness change must be pinned by tests like the existing several-dependencies pin (commit 9913dd6). Splitting could launder a `revise` that really needed a human. Hence the rules above: never split a reject, a denylist hit or a human-decision defer, and the shared attempt budget keeps the escalation trigger. More LLM calls per hard node.

## Lens: status-model
### Explicit node transition table, checked against the previous plan (plan-lint --base)
- Verdict: **revise** · priority high · effort M
- Problem: The node statuses are explicit and machine-checked, but transitions are not. plan-lint is a state check: it confirms that each row's current status agrees with the records it cites, and it never compares the plan with its previous version. Two rules exist only as prose. Escalated must never be reset by the loop, only by the human it waits on. A deferred-to-ready reset must cite new evidence ('no citation, no reset'). plan-lint checks neither for a ready node, so a hand edit that turns an escalated or deferred node back to ready, keeping its HOLDed record, passes clean. Nothing stops a done node going back to ready either, apart from the [reused-id] warning.
- Evidence: .claude/memory/loop-plan.md:22 (status vocabulary only, no transitions); .claude/memory/loop-plan.md:79-84 (deferred→ready needs a cited record or check output: prose only); .claude/memory/loop-plan.md:92-94 (escalated is moved only by the human's answer); .claude/loop.md:110 ('never reset an escalated node — only the human it waits on can'); scripts/trace/plan.mjs:251-294 (record checks run for done, deferred and escalated only; ready is never checked); scripts/trace/plan.mjs:295-302 (a ready node with its own record gets only the [latest] warning); scripts/trace/plan.mjs:196 (planViolations takes the current plan and the store, no prior plan)
- Critic proposal: 1. Add a 'Transitions' table to loop-plan.md (from → to → required evidence) and export it from plan.mjs as TRANSITIONS. Legal moves and their evidence: (none)→ready/blocked/deferred/escalated (origin cites a critic record); ready→in-progress (dispatch); in-progress→done (own loop:<id> accept/qualify + CLEAR, as today); in-progress→deferred/escalated (HOLDed record); in-progress→ready (only with a run-log citation of error/budgetStopped or a revise record); deferred→ready (notes cite a TR id newer than the node's record, or the record's failed_gates include agent-failed/base-mismatch, or writer loop/apply-check:); escalated→ready/blocked (only with a record whose writer_id starts 'human:', or a CLEAR by actor 'human' on the HOLDed record); any live→dropped (notes give a reason). done is terminal (to dropped only via pruning). 2. Add planTransitionViolations(prev, cur, state), wired as `pnpm trace plan-lint --base <git-ref>` (cli.mjs reads `git show <ref>:.claude/memory/loop-plan.md`; plan.mjs stays pure). It emits [illegal-transition] for a move not in the table and [transition-evidence] for a legal move that lacks its evidence. 3. In loop.md step 9, make the re-plan run `plan-lint --pre-dispatch --base HEAD`. 4. Add a state-only fallback that needs no git, for direct edits: [unsupported-reset], an error when a ready node's own record carries a HOLD and its notes cite no other existing TR id (the exemptions above apply).
- **Skeptic repair (binding, replaces the proposal):** Drop plan-lint --base. Add a prose 'Transitions' table to loop-plan.md for documentation. Add state-only rules to planViolations. (1) [unsupported-reset], an error: a ready or blocked node whose cited record (own or critic) carries a HOLD and is escalation-grade (revise, reject, or a defer whose missing matches HUMAN_DECISION, or a denylist defer), unless the record carries a documented human-release action. Define that action's convention (actor/consumer and note) in topics/trace.md. (2) [unsupported-reset], an error: a ready node whose own defer record is HOLDed and whose notes cite no newer TR id. Exempt agent-failed, base-mismatch and loop/apply-check records, and exempt a run-log citation for an infra-error reset, or the rule raises false positives on the infra path step 10 already sanctions. (3) Promote [reused-id] to an error when the node's own cited record is the CLEARed one, so a done node cannot be moved back to ready. plan.mjs sits under the scripts/ denylist, so a human applies this change, with parity tests extended.
- Skeptic reason: The gap is real. In planViolations (plan.mjs ~251-315), record checks run only for done, deferred and escalated nodes. A ready or blocked node gets the [latest] warning on its own record and nothing at all on a critic record. A hand edit that moves an escalated or deferred node back to ready, keeping its HOLDed record, therefore passes clean, and the rules in loop.md:110 ('never reset an escalated node') and loop-plan.md 'no citation, no reset' exist only as prose. The git --base mechanism is the wrong check, though. CLAUDE.md allows commits only when the user asks, so HEAD's loop-plan.md can be many iterations behind. Diffing HEAD against the current plan collapses several legal hops into one illegal-looking move: ready→in-progress→done would read as ready→done, and deferred→ready→in-progress→deferred would read as no move or a wrong one. It would raise false [illegal-transition] errors, or the loop would learn to ignore it. A legal deferred→ready reset and an illegal escalated→ready reset look the same in the table. They differ in the record's verdict and its consumer actions, which the store already holds, so a state-only check is enough.
- Research basis: Workflow-engine/issue-tracker transition validators (Jira workflows, BMAD's Draft→Approved→In progress→Review→Done with a human gate on Approved). Beads' closing a blocker as the event that releases dependents.
